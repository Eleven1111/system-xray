# 报告骨架（单一模板）

> 默认交付：**一份 Markdown 报告 + 一份结构化 analysis JSON**。
> HTML / Obsidian 素材属于按需导出，不用"三件套齐全"定义分析完成。
> 本文件只管**结构与内容义务**；渲染样式（HTML class、雷达图、折叠块）与分析规则分离，
> 见 `agent/prompts/system.md`。

报告由结构化记录生成，不是反过来。每个章节的内容都应能在 analysis JSON 里找到对应对象。

---

## 1. 决策摘要

- 目前**最重要的判断**（结论前置，一句话讲完）
- **建议动作**及其执行者
- 主要不确定性与**适用边界**
- 是否存在影响当前决策的 `needs_review` 对象

证据不足时允许写不确定判断——"尚不能区分需求下降与测量变化"是合格的摘要句，
"需要进一步观察"不是。

## 2. 系统边界与目标

分析对象、纳入与排除了哪些主体、评价目标是谁的目标、`as_of` 截止时间。
若做过边界敏感性检查且结论对边界敏感，**在这里写清依赖**。

## 3. 已知事实与未知

- 关键证据（可点击追溯到具体摘录）
- 未决冲突及其影响范围
- 数据覆盖与口径限制
- 覆盖审计里对当前决策有实质影响的 `unknown` 项

## 4. 核心机制与替代解释

通常深入 **1-3 条**机制，不做七维等长铺陈。每条给：

机制链 → 支持与反对的断言 → **至少一个替代解释** → 鉴别预测 → 失效条件 → 对行动的影响。

敏感性结果在这里落地，逐条标 **结论稳健 / 依赖关键假设 / 证据不足以区分**。

## 5. 动态变化与条件未来

- 延迟、存量、阈值
- 条件情景（**没有默认三分法**；概率可选，非概率分布时明确标注）
- 近期可裁定预测（含 `event_type` 与裁定窗口）
- 长期适应路径：现在做哪一步、保留哪些选项、什么信号触发切换、切换需要多少提前量

## 6. 行动卡

每条行动给执行者、最小下一步、验证设计、护栏与停止条件、下一次决策触发条件。
超出读者权限的行动不写成可执行承诺。

## 7. 判断变更记录（重复分析时）

新增 / 撤回 / 修订 / 保留的判断，各自的**变化类型**
（系统状态 / 机制 / 观测口径 / 分析修正）与理由。
纠错首先服务准确性和审计——**不要求把纠错过程写成文学情节**。

## 8. 审计附录

- 要素覆盖矩阵（`coverage_audit`）
- 断言—证据关系（逐条 URL + 摘录位置 + 来源家族，由 `--build-audit` 机械生成）
- 方法假设与因果能力级别（L1/L2/L3）
- 完整性状态（`draft` / `partial` / `complete_with_uncertainty`）与版本
- 本次未做的事（预算耗尽项、`deferred_gaps`）

---

## 精简模式

缩短叙述，**不删**：关键证据、核心替代解释、行动条件、信源审计。
读者仍须能沿一条主张追溯到具体摘录。

## 写作约束（与结构无关，但同样强制）

- 章节标题可以结论前置（判断句），但不得为了句式牺牲准确性。
- 禁用空心大词：赋能、协同、价值创造、抓手、闭环。
- 少铺陈多结论、少泛化多取舍、少大词多人话；MIT Technology Review 式克制。
- 不预写结论：报告里的每个判断都必须在分析完成后才能确定。
